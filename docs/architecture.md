## Архитектура — шаг 3, решено 09.11.2026

### Решения

| Что | Решение | Почему |
| --- | --- | --- |
| Раскладка | **Сначала слои** (`domain/`, `data/`, `ui/`), фичи — только внутри `ui/` и `data/repositories/`. Feature-first не берём (09.11) | Так устроено эталонное [Compass app](https://github.com/flutter/samples/tree/main/compass_app) от Flutter. Слои сверху понятнее в небольшом приложении, и границу слоёв видно сразу. Цена: фича размазана по трём папкам, её сложнее удалить или вынести в пакет — feature-first лучше масштабируется. |
| Проект | **Один Flutter-проект**, без pub workspace | Workspace нужен для общего кода с сервером на Dart, для границ, которые проверяет компилятор (`domain` — отдельный пакет без `flutter`), и для переиспользования между приложениями. Сейчас ни то, ни другое, ни третье: сервер будет не на Dart. Вернёмся на шаге 2б |
| Ошибки | **Sealed-исключения** на область: `WalkFailure`, `PurchaseFailure`… Реализация в `data/` ловит `DioException`, `PlatformException`, ошибки SDK и бросает свои. Блок ловит `on PurchaseFailure` и разбирает `switch` с проверкой полноты | Меньше кода, чем `Result`, и привычнее для BLoC. Цена: компилятор не заставит поймать ошибку — нужен тест на путь ошибки в каждом блоке |
| Папка | `~/Documents/Development/walks`, рядом с `mobile-app`; потом публичный репозиторий на GitHub | Отдельный репозиторий (перенесено 09.11) |
| DI | **get_it без кодогенерации** (11.11, вместо `RepositoryProvider`). Регистрация руками в `app/di.dart`: репозитории и сервисы — `registerLazySingleton`, блоки — `registerFactory`. Блок по-прежнему получает интерфейсы в конструкторе. `getIt` вызывает `app/` и тонкая `Page` экрана в `ui/` (решено 11.11, см. правила в «Структуре») | Самый распространённый DI во Flutter. Весь граф виден в одном файле, без build_runner. Цена: файл правим руками на каждый новый класс; забытая регистрация — ошибка при запуске, а не при сборке. `injectable` (аннотации и кодогенерация) — следующий шаг для изучения, см. «Стек» |

### Структура

```
lib/
  main.dart
  app/                        корень композиции: App, router, di.dart (регистрация и выбор реализаций)
  domain/
    models/                   Day, Progress, Progression, Goal, Product… — чистый Dart, freezed
    repositories/             интерфейсы: WalkRepository, LocationSource, SubscriptionRepository,
                              AuthRepository, CheckoutGateway, AdsService, CrashReporter…
    rules/                    правила: функции над моделями, «сейчас» — параметром
    failures/                 sealed-исключения по областям
    use_cases/                только когда логика собирает несколько репозиториев (гайд Flutter)
  data/
    repositories/<область>/   fake_….dart, <вариант1>_….dart, <вариант2>_….dart
    services/                 обёртки SDK; WalksApi + FakeWalksApi — фейковый сервер в памяти
  ui/
    core/                     общие виджеты, тема
    <экран>/                  bloc/, widgets/, <экран>_page.dart, <экран>_view.dart — walk, history, paywall, auth, shop
test/                         зеркалит lib/; contracts/ — общие наборы тестов на интерфейсы
```

**Правила — проверяются импортами на ревью:**

- `domain/` импортирует только Dart, `clock` и `freezed_annotation`. Ни `flutter`, ни `dio`, ни SDK.
- `data/` реализует интерфейсы из `domain/` и переводит чужие ошибки в свои sealed.
- `ui/` знает только `domain/`. Блок принимает интерфейс в конструкторе, а не `Fake…` или `Drift…`.
- Экран — пара **Page/View** (решено 11.11). `<экран>_page.dart` — тонкая: только `BlocProvider(create: (_) => getIt<…Bloc>())` и `View`; кроме `app/`, `getIt` вызывает только она. `<экран>_view.dart` — вся вёрстка, блок берёт из `context`, о get_it не знает. Widget-тесты проверяют `View` с фейковым блоком, глобальный `getIt` им не нужен.
- Конкретные реализации видит только `app/`.
- Экраны не импортируют друг друга; общее — в `ui/core/` или в `domain/`.

### Выбор реализаций — решено 11.11.2026

Реализацию выбираем **в коде**, а не в запущенном приложении. В `app/di.dart` на каждую область — `switch` по значению enum: правишь одну строку и перезапускаешь. Компилятор проверяет, что все варианты разобраны. Флаг сборки `--dart-define` поверх этого добавим, когда дойдём до CI.

Переключение на лету через меню разработчика (решено 09.11: `KeyedSubtree` с ключом от выбора, свой `GoRouter` на каждый набор, выбор в `shared_preferences`) отменено 11.11: сложность пересоздания дерева не окупается, сравнивать реализации можно и пересборкой.

### Настройки — решено 11.11.2026

Хранилище «ключ–значение» (`shared_preferences`) — такой же внешний источник, как база: интерфейс в `domain/repositories/`, реализация в `data/`. `app/` и `ui/` не ходят в пакет напрямую. Применим при первых настоящих настройках (время напоминаний).

### Отчёты о падениях (область 0) — решено 11.11.2026

- Интерфейс `CrashReporter` — только общее у Crashlytics и Sentry: `recordError(error, stack, {fatal, reason})`, `log(message)`, `setUserId(id)`, `setKey(key, value)`. Производительность — отдельная область, не здесь.
- Перехватчики `FlutterError.onError` и `PlatformDispatcher.instance.onError` ставит `app/` один раз — функция `installErrorHandlers(CrashReporter)`, её вызывает `main` после `configureDependencies()`. Реализации о перехвате не знают, `domain/` не знает о `FlutterErrorDetails`.
- Фатальность. Крючок не знает контекста, поэтому ставит значение по умолчанию: ошибки фреймворка (`FlutterError.onError`: build, layout, paint — пользователь видит серый экран) — фатальные, непойманные асинхронные (`PlatformDispatcher`) — нефатальные. Важные сценарии (открыть главу, покупка, сохранение шагов) крючку не оставляем: блок ловит ошибку на месте, сам решает `fatal` и показывает состояние ошибки. Частые нефатальные отслеживаем оповещениями в панели. Нативные падения SDK ловит сам, всегда фатальными.
- **Исключение из правила ошибок:** у `CrashReporter` нет sealed-исключений, он никогда не бросает. Реализация ловит свои сбои внутри и пишет в консоль. Причина: `recordError` вызывают из `catch` и крючков, когда что-то уже сломалось. Если он бросит, код после него (показ ошибки пользователю) не выполнится, а в крючке ошибка может уйти по кругу. Проверяется контрактным тестом «не бросает, даже если SDK сломан».
- Лог-след: переходы, действия пользователя, начало и конец важных операций, с меткой источника (`[steps] …`). Частые события (точки GPS, тики шагомера) не логируем — вытеснят полезное из буфера.
- **Настройки Firebase в репозитории (12.11.2026).** `lib/firebase_options.dart`, `google-services.json` и `GoogleService-Info.plist` коммитим, хотя репозиторий публичный. API-ключ Firebase в клиенте — идентификатор проекта, а не секрет: он и так извлекается из APK. Данные защищают Security Rules и App Check, а сам ключ в Google Cloud ограничен по API. С 12.11.2026 у Android- и iOS-ключей оставлен только Firebase Installations API (Firebase по умолчанию разрешал 25 API). Crashlytics отправляет отчёты на `crashlyticsreports-pa.googleapis.com`, этот адрес ключ не проверяет. Подключая новый сервис Firebase (FCM и т. д.), добавляем его API в список. Ограничение по приложению (пакет + SHA-1) отложено до flavors в этапе F: debug-ключ подписи в CI каждый раз новый, и с SHA-1 от одной машины отчёты из сборок CI перестали бы доходить. Цена: ложные письма «ключ утёк» от GitHub и Google. Отказались от `.gitignore` и секретов в CI — сложнее, а защищённее не становится.
- **Сбор в debug (12.11.2026).** Пока включён: отчёты идут и из debug-сборки, чтобы видеть работу Crashlytics. Когда появятся пользователи — стандартная практика: `setCrashlyticsCollectionEnabled(!kDebugMode)`, иначе ошибки разработки засоряют панель и метрику crash-free. На iOS при подключённом отладчике нативное падение перехватывает отладчик — для проверки запускать без него.
- **Проверено 12.11.2026 на эмуляторе Android, debug:** нефатальная, ошибка фреймворка, асинхронная и нативное падение доходят до Crashlytics; нативный отчёт уходит при следующем запуске. Тестовые ошибки — из меню разработчика (`ui/dev_menu/`), нативное падение — через свой канал `dev.ettynat.stepfold/debug`, без привязки к SDK. Release-сборка (mapping-файл, символикация) и iOS (dSYM, `uploadDebugSymbols`) — вместе с flavors, этап F.

### Marionette — решено 12.11.2026

- **Что это.** `marionette_flutter` (LeanCode) — binding в приложении, через VM service отдаёт агенту дерево виджетов и принимает нажатия и ввод. Для автотестов не используется, для них Patrol.
- **Где включена:** debug и profile, условие `!kReleaseMode`, как у меню разработчика. В release нет VM service, а ветку с `MarionetteBinding` вырезает tree shaking (в profile-сборке символы есть, в release проверить не удалось: сборка падает на загрузке mapping-файла Crashlytics, см. этап F).
- **Где код:** развилка binding прямо в `main.dart`, пока это одна строка. Вынесем в `app/`, когда появится `MarionetteConfiguration` для своих компонентов UI-кита.
- **Зависимость:** `marionette_flutter` в `dependencies`, а не в `dev_dependencies`: его импортирует код из `lib/`.
- **Как управляет агент:** CLI `marionette_cli` с обёрткой `adrive` на машине разработчика, не MCP-сервер `marionette_mcp`: ответы короче, адрес VM service находится сам. На код проекта выбор не влияет. Версии CLI и пакета должны совпадать (0.7.0).

### Модель продвижения (C1) — решено 12.11.2026

Правила продукта — в [product.md](product.md) («Правила продвижения», «Выбор цели»). Здесь — как они устроены в коде, `lib/domain/models/`.

- **Что храним, что вычисляем.** Храним дни (`DaySteps`: авто и вручную), траты (`Spending`: открытая глава или купленная медаль, с заплаченной ценой и моментом) и текущую цель. Запас, бронзу, доступные главы и серию вычисляем. Журнал событий не берём: два журнала с разных устройств трудно объединить.
- **Модели — данные, правила — функции в `domain/rules/` (12.11.2026).** Метод живёт в модели, только если ему хватает её собственных данных (`Progress.reserve`, `DaySteps.counted`, `Medal.price`). Всё, чему нужна другая модель или время, — функция верхнего уровня в файле по теме: `chapters.dart`, `medals.dart`, `goal.dart`, `streak.dart`, `manual_entry.dart`. Пример: `openChapter(progress, progression, id, now: …)` возвращает новый `Progress`, отказ — sealed `ProgressFailure` (`NotEnoughSteps`, `ChapterUnavailable`, `MedalUnavailable`). «Сейчас» правила получают параметром `now`/`today`, сами `clock` не читают — его читает вызывающий (блок или use case). Не берём: правила методами `Progress` (разрастается в божественный объект и знает про каталог), изменяемые сущности (BLoC нужны неизменяемые состояния), классы-сервисы без состояния (Effective Dart: не делать классы только со статическими членами), use cases в C1 (сразу нужны репозитории). Use cases появятся в C4 тонкой обёрткой: прочитали → вызвали правило → сохранили.
- **Запас — `шаги − траты` без обрезки нулём**, минус — долг ([product.md](product.md), 12.11.2026). Зачёт дня — `auto + manual`, где `manual` — ручная добавка.
- **Модели — freezed.** Правило слоёв расширено: `domain/` импортирует Dart, `clock` и `freezed_annotation` (аннотации — чистый Dart). Сгенерированные `*.freezed.dart` коммитим: CI не запускает build_runner. После правки модели — `fvm dart run build_runner build`.
- **День — свой тип `Day`, момент — `DateTime` в UTC.** `Day` хранит номер дня с 1970-01-01, его даёт местная дата устройства (`Day.fromLocal`, `Day.today()` через `clock`). `DateTime` в полночь не берём: `==` учитывает часы и UTC, а `add(Duration(days: 1))` ошибается в день перевода часов. Epoch-миллисекунды для дня не подходят: полночь 12.11 в разных поясах — разные числа. Перелёт: день становится длиннее или короче, дата может пойти назад — шаги пишутся в уже существующий день, сумма и запас не меняются.
- **Ручной ввод** — проверка `checkManualEntry` в `rules/manual_entry.dart`, запрет `ManualEntryLock` в `models/manual_entry_lock.dart`.

### Разрешения (C2а) — решено 12.11.2026

Один сервис на все разрешения приложения, а не разрешения внутри каждой области: всё в одном месте, «открыть настройки» и «отказали навсегда» решаются одинаково.

- **Интерфейс** `PermissionService` в `domain/repositories/`: `status(p)`, `request(p)`, `openSettings()`. Разрешение — `enum AppPermission`; значение добавляет область, которой оно нужно.
- **Статусы — по действию экрана, а не по платформе:** `granted` (работаем), `canRequest` (кнопка «Разрешить», будет системный диалог), `blocked` (диалога не будет — «Открыть настройки»), `unavailable` (нет на устройстве или запрещено родительским контролем). Платформенные состояния — Android «отказали навсегда», iOS `notDetermined`/`denied`/`restricted`/`limited` — сводит к ним реализация. HealthKit не сообщает о запрете чтения: после запроса — `granted`, запрет виден как ноль шагов.
- **Изменения статуса — без потока.** Блок перепроверяет `status()`, когда приложение возвращается на экран (`AppLifecycleListener` в `ui/`). Платформы не присылают событие «разрешение изменилось», а при отзыве в настройках Android и iOS убивают процесс.
- **Кто решает, когда спрашивать** — блок: сначала своё объяснение, потом системный диалог (на iOS он бывает один раз, на Android — два). Как спрашивать — реализация в `data/`; `BuildContext` ей не нужен.
- **Фейк** задаёт статусы и ответ на запрос. Настоящая реализация и выбор пакета — этап D.

### Источник шагов (C2) — решено 12.11.2026

- **Интерфейс** `StepSource`: `stepsByDay(from, to)` дозабирает прошлые дни, `watchToday()` — живой счётчик сегодня. Только запрос не обновляет «сегодня», только поток теряет дни, когда приложение не открывали.
- **Возвращает `DayCount(day, steps)`**, а не `DaySteps` и не голые числа: каждое число несёт свой день, после полуночи ясно, к какому дню оно относится; ручная добавка — не дело источника.
- **Дни без данных пропускаются**, ноль не подставляется: «нет данных» и «0 шагов» — разное (как `DaySteps.auto == null`).
- **Разрешения** — через `PermissionService` (C2а). Источник называет нужное разрешение: `requiredPermission` (датчик — `activityRecognition`, хранилище здоровья — `healthSteps`); блок передаёт его сервису. Смена источника меняет и разрешение, `di.dart` трогать не надо.
- **Ошибки** — sealed `StepSourceFailure`: `StepPermissionDenied` (разрешение отозвали во время работы), `StepSourceUnavailable`. Префикс `Step` — чтобы не столкнуться с ошибками разрешений других областей.
- **Фейк управляемый:** `setSteps` (в том числе поздние шаги за прошлый день), `failNext` для запроса, `failWatch` для потока; «сегодня» — через `clock`. Поток при подписке сразу отдаёт текущее число, если за сегодня есть данные.
- **Два источника сразу** (хранилище здоровья, при недоступности — датчик) — если решим на этапе D, это третья реализация `StepSource`, которая выбирает между двумя; интерфейс не меняется. Тогда же: при отказе в хранилище молча переходить на датчик или спрашивать.
- **Читает ли экран шаги из источника или из базы** — развилка C4.

### CI — решено 12.11.2026

GitHub Actions, `.github/workflows/ci.yml`, на каждый PR в `main` и push в `main`. Версия Flutter — из `.fvmrc`, одна на машину и CI. Две параллельные задачи:

- **Проверки:** `dart format --set-exit-if-changed`, `flutter analyze --fatal-infos` (подсказки линтера тоже валят сборку), `flutter test --coverage`. Процент покрытия — в сводке запуска, `lcov.info` — артефактом на 14 дней. Порога покрытия нет.
- **Сборка Android:** `flutter build apk --debug` на Java 17 — проверяем, что нативная часть собирается.

**Слияние PR (решено 12.11.2026).** Каждый PR в `main` ставится на автослияние (merge commit) и сливается сам, когда обе проверки зелёные. Защита `main`: проверки «Format, analyze, test» и «Build Android APK» обязательны; ветка должна быть свежей (`strict`) — PR, отставший после слияния другого, обновляется от `main` (`gh pr update-branch`) и проверяется заново. Иначе два PR, зелёных по отдельности, могут вместе сломать `main`. Ветка удаляется после слияния. Ревью не требуется, на администратора правило не действует. Merge queue недоступна (личный аккаунт, не организация).

### Порядок работ — решено 11.11

Пересмотрено 11.11.2026 ([вопрос 16](open-questions.md)): сначала настоящие инструменты и ядро по одной реализации, вторые реализации — в самом конце. Заменяемость доказывает пара «фейк + одна настоящая». Инструмент подключаем, когда его есть чем проверить: Analytics — с первыми экранами, FCM — когда есть что слать, flavors dev/prod — позже, ради знакомства с ними, не позднее первой сборки, которую ставят на чужой телефон. ## Стек — кандидаты по умолчанию (черновик 29.10.2026)

Окончательный выбор пакета — на разборе области, чаще всего это два варианта, а не один. Строка «Сервер» отменена: сервер будет на другом языке, выбираем в самом конце.

### Что — чем — почему

| Что | Чем | Почему так |
| --- | --- | --- |
| Состояние | flutter_bloc | Самый распространённый подход в индустрии, bloc_test проверяет блок как цепочку состояний. Riverpod не берём |
| Зависимости | get_it, регистрация руками (решено 11.11, см. «Решения»). Потом, для изучения: `injectable` — регистрация аннотациями на классах и кодогенерация через build_runner | Голый get_it проще читать и объяснять. `injectable` часто встречается на коммерческих проектах; его «окружения» рассчитаны на dev/prod целиком, а не на выбор по каждой области |
| Навигация | go_router, `StatefulShellRoute` | Гарды: пейволл на закрытых экранах, переход по пушу и уведомлению на сводку |
| Модели | freezed + json_serializable в `shared/` | Чистый Dart, поэтому работает и на сервере. Sealed-классы под состояния подписки и заказа, `switch` с проверкой полноты |
| Локальная база | drift (SQLite) | Запросы с `watch()` дают Stream, и история сама обновляется после сохранения прогулки. Типобезопасный SQL, миграции с тестами (`drift_dev schema`). |
| Сеть | dio + интерцептор JWT с обновлением по refresh-токену | обновление токена на 401 с очередью запросов, интерцептор свой |
| Хранение токенов | flutter_secure_storage | Keychain и Keystore. В отличие от shared_preferences, токен не лежит открытым текстом |
| Карта | flutter_map + тайлы OSM | Без ключа и аккаунта. По правилам OSM указать `userAgentPackageName` и атрибуцию; для личного проекта нагрузка допустима |
| Геолокация | geolocator | Поток позиций с `distanceFilter`, свой фильтр шума по точности и скорости — под unit-тесты |
| Локальные уведомления | flutter_local_notifications + timezone + flutter_timezone | `zonedSchedule` с поясом устройства. Других пакетов с такой полнотой нет |
| Пуш | firebase_messaging; сервер шлёт через FCM HTTP v1 (`googleapis_auth`, сервисный аккаунт) | Старый legacy API закрыт, v1 — с OAuth-токеном сервисного аккаунта. Без платного аккаунта Apple — только Android |
| Подписка | Вариант 1 — in_app_purchase (StoreKit 2) + проверка чека на своём сервере; вариант 2 — RevenueCat | Вариант 1 — полный контроль: покупка, восстановление, состояния, проверка на сервере. Вариант 2 — то, что берут в продукте ради времени; работает без своего сервера, поэтому идёт первым (этап E). Поддержку StoreKit 2 в `in_app_purchase_storekit` проверить при старте |
| Реклама | google_mobile_ads с **тестовыми ID Google** | AdMob — самая распространённая рекламная сеть. На время разработки аккаунт не заводим: тестовые app ID и ID блоков Google работают без аккаунта. Yandex Mobile Ads (`yandex_mobileads`, демо-блоки без регистрации) — вторая реализация `AdsService`, если останется время |
| Вход | Google — flutter_appauth (authorization code + PKCE, клиент типа iOS/Android без секрета). Второй популярный провайдер, кандидат VK ID, решаем при реализации | Google разрешает публичный клиент. GitHub не используем (09.11): для обычного пользователя такой вход выглядит странно |
| Мерч | Сначала Stripe в тестовом режиме (`flutter_stripe`, PaymentSheet). Если аккаунт не заведётся — bePaid (оплата через страницу bePaid в браузере или WebView, тестовая карта `4200 0000 0000 0000`) | У Stripe родной PaymentSheet и 3DS. bePaid — белорусский шлюз: нужен для местных пользователей, но готового Flutter SDK не нашёл. Схема одна: сервер создаёт платёж, приложение показывает оплату, итог приходит вебхуком |
| Сервер | Не на Dart; язык и фреймворк выбираем в самом конце | До этого — `FakeWalksApi` в памяти |
| Вебхуки на локальный сервер | cloudflared quick tunnel | Публичный HTTPS-адрес без аккаунта — Stripe или bePaid смогут достучаться до ноутбука |
| Время в логике | пакет clock | Граница 7 дней, полночь и пояс тестируются с подменой «сейчас», без `DateTime.now()` в логике |
| Тесты | test, mocktail, bloc_test, drift в памяти (`NativeDatabase.memory()`) | Репозитории тестируются на настоящей SQLite в памяти, а не на моках |
| Линтер | very_good_analysis | Строгие правила, единый стиль кода |
